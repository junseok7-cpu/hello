# 프롬프트와 AI 에이전트 설계

출처: Google AI Studio 가이드·실습 (notes/google-ai-studio/), Agentic AI 1~11장 (notes/agentic/)

## 프롬프트 기본

- **구체적으로**: 대상 독자, 어조, 분량, 형식을 적는다. ("20대 IT 입문자 대상, 친근한 어조, 500자 내외")
- **역할(페르소나)**: "20년 경력 개발자로서 이 코드를 검토해라"처럼 역할을 준다.
- **퓨샷**: 입출력 예시를 2~5개 넣는다. 서식(태그·공백·기호)을 통일하고, 가장 흔하고 중요한 사례를 앞에 둔다. 좋은 예시와 함께 **나쁜 예시**도 보여 준다.
- **분해**: 프롬프트 체이닝(앞 출력이 다음 입력)과 응답 집계(나눠 처리한 뒤 합침).
- **구조화된 출력**: "CSV로", "스프레드시트에 붙여 넣기 좋은 표로", "Matplotlib 코드로" 요청하면 바로 분석에 쓸 수 있다.
- **매개변수**: 온도가 낮으면 일관성, 높으면 다양성이 커진다. 최신 모델은 XML/마크다운 태그로 구획을 나누면 지시를 더 잘 따른다.
- **긴 텍스트 분석**: 소설 전체를 넣고 서사 구조, 인물 관계, 장별 감정 점수를 표로 뽑은 뒤 차트로 잇는다. **AI가 만든 숫자는 오차가 있으므로 원문으로 검증하고, 경향 파악에 쓴다.**

## 시스템 프롬프트 6요소

| 요소 | 내용 |
|---|---|
| 역할 | 정체성과 담당 직무 ("AI 어시스턴트" 말고 "반품 처리 담당자"처럼 직함으로) |
| 맥락 | 과업에 필요한 배경 지식, 접근 가능한 자료 |
| 규칙 | 꼭 할 것과 절대 하지 말 것 ("확인 없이 환불을 확약하지 마라", "모르면 추측하지 말고 묻는다") |
| 형식 | 구조, 분량, 문체, 시작과 끝 |
| 예시 | 입출력 쌍 1~5개 (정확도가 크게 오른다는 보고가 있음) |
| 중단 조건 | 즉시 멈추고 사람에게 넘길 조건과 그때의 행동 |

**4대 실패**: 모호한 역할(범위가 멋대로 넓어짐), 예시 누락(형식이 매번 바뀜), 중단 조건 부재(Air Canada 챗봇 판결: 회사가 챗봇의 잘못된 안내에 배상 책임을 짐), 서로 모순되는 규칙("간결하되 빠짐없이 상세히"). 뿌리는 하나다: 적지 않은 빈칸을 모델이 알아서 채워 주길 기대한 것. 최신 모델일수록 지시를 문자 그대로 따른다.

**테스트 먼저**: 프롬프트를 쓰기 **전에** 실제 입력 20~50개(표준 사례, 경계 사례, 악의적 입력)를 스프레드시트로 만든다. 돌려 보고, 실패를 고치고, 다시 돌린다. 프롬프트도 버전 관리한다.

## 에이전트를 만들기 전 5가지 질문

1. 자동화할 **구체적 워크플로**는?
2. 결과에 책임질 **한 사람**은?
3. 사람의 **검토 지점**은 어디이고 얼마나 자주인가?
4. 개선될 **지표**와 도입 전 **기준점**은?
5. 첫 실수가 나면 **무엇을 다르게** 할 것인가?

하나라도 비어 있으면 코드보다 그 빈칸부터 채운다.

## 자율성 5단계: 문제를 안정적으로 푸는 가장 낮은 단계를 고른다

1. 프롬프트 기반 보조 (초안, 요약, 분류)
2. 워크플로 자동화 (정해진 순서대로)
3. 도구 연동 에이전트 (실시간 데이터 조회 후 사람이 승인): 대부분의 첫 배포에 적합
4. 감독하의 자율 (표준 사례는 직접 처리, 예외만 사람에게)
5. 다중 에이전트 (2~4단계 기반이 없으면 혼란만 키움)

## 설계 도구

- **에이전트 브리프 (1쪽)**: 책임지는 결과물, 누구를 대신하나, 누가 결과를 받나, 권한의 시작과 끝, 실패 시 처리.
- **워크플로 4요소**: 트리거(구체적 이벤트), 작업(단계별), 출력(형식 고정), 핸드오프(누가 받아서 무엇을 하나).
- **가역성 테스트**: "실수를 쉽게 되돌릴 수 있나?" 예(초안, 내부 메모, 태그)면 자동화 후보이고, 아니오(발송, 삭제, 결제)면 사람의 최종 승인을 거친다.
- **권한은 실적으로 넓힌다**: 읽기 전용 → 초안·제안 → 제한된 실행 → 넓은 자율.
- **누적 오차**: 0.85¹⁰ ≈ 0.20. 짧고 좁은 단계로 시작하고, 검증된 뒤에 잇는다.
- **7대 구성 요소**: 모델, 시스템 프롬프트, 메모리, 도구(MCP), 오케스트레이션(반복 상한·비용 상한·중단 규칙), 의사결정 루프, 인터페이스.

## 고장 진단

| 증상 | 원인 | 대응 |
|---|---|---|
| 낡거나 틀린 정보를 확신 있게 말함 | 질 낮은 검색 문맥 | 출처 신뢰도, 최신성 필터, 유사도 임계값 |
| 비슷한 입력에 다른 결과, 인자 지어냄 | 모호한 규칙 | 규칙 구체화, 나쁜 예시, 출력 검증 |
| 엉뚱한 도구 호출 | 도구가 너무 많거나 설명이 겹침 | 도구 줄이기, 서로 배타적인 설명, 엄격한 스키마 |
| 무한 루프, 에스컬레이션 안 함 | 완료·위험·불명확 기준 없음 | 반복·비용 상한, N회 실패 시 사람 개입 |

같은 실패가 반복되거나 지시를 덧붙일수록 나빠지면 프롬프트가 아니라 **아키텍처** 문제다.

## 다중 에이전트 패턴

- **선형 파이프라인**: 접수 → 분류 → 초안 → 검증. 처음엔 이것부터. 작은 모델 여러 번 호출이 큰 모델 한 번보다 싸고 빠를 수 있다.
- **라우터**: 입력 유형별로 다른 경로로 보낸다.
- **병렬 분산**: 독립 작업을 동시에 하고 합친다.
- **사람 확인점**: 중요한 결정 앞에 사람 승인을 둔다.
- 프레임워크: LangGraph, CrewAI, AutoGen, OpenAI Agents SDK 등. 디버깅이 어려우면 단순화를 먼저 검토한다.

## 운영·거버넌스 메모

- 프롬프트 표류, 토큰 비용, 배포 전 검증을 모니터링한다. 정기 검토 후 확장·재설계·폐기를 판단한다.
- 무감독 에이전트에 민감 데이터를 맡기지 않는다. 최소 권한, 감사 로그, 가드레일, 레드팀 테스트(프롬프트 인젝션: 직접형·간접형).
- 사람의 책임: 자동화 편향(AI 출력을 그대로 믿는 경향)을 경계하고, 승인자가 실제로 검토하도록 워크플로를 설계한다.
- 보고할 때는 "도입했다(채택)"와 "업무가 실제로 바뀌었다(흡수)"를 구분해서 정직하게 쓴다.
