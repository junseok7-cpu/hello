# 명세 주도 개발 (AI 통합 프로세스)

출처: 슬라이드 "명세 주도 개발" (slides/20260814.html)

## 왜

- 가장 어려운 건 코드가 아니라 **무엇을 만들지 정하고 모두가 같은 이해를 유지하는 것**이다.
- 코드 우선 방식은 급한 기능이 덧붙을 때마다 구조가 무너지는 "발코니 아키텍처"를 만든다.
- AI 코딩 도구는 잘못된 것도 빠르게 만든다. 그래서 **의도(intent)**를 중심에 둔 명세가 기준이 되어야 한다.

## 원칙

- 명세가 단일 진실의 원천이자 실행 가능한 계약이다. 코드·테스트·문서는 명세에서 파생된다.
- 꼭 필요한 산출물만 만든다. 안정적인 ID로 의도 → 구현을 추적한다. 최종 결정은 사람이 한다. 명세도 Git에 텍스트로 둔다.

## 세 가지 산출물

1. **요구사항 카탈로그**: 기능(FR), 비기능(NFR), 제약(C)을 ID와 함께 표로 적는다.
2. **엔티티 모델**: 도메인 명사, 속성, 타입, 검증 규칙. Mermaid/PlantUML로 그린다. 용어집 역할을 한다.
3. **시스템 유스케이스**: ID, 제목, 액터, 목표, 사전 조건, 메인 플로우, 대안 플로우, 예외 플로우, 사후 조건, 비즈니스 규칙(별도 ID), 연결된 요구사항.

## 좋은 명세의 조건

- 두 사람이 읽고 같은 결과를 떠올리고, 테스터가 인수 조건을 바로 뽑을 수 있다.
- AI가 빠진 규칙을 지어낼 필요가 없을 만큼 정밀하다.
- 내부 구현이 아니라 **밖에서 관찰 가능한 동작**을 능동태로 쓴다.
- "보통", "빠르게", "필요에 따라" 같은 말 대신 명시적 규칙을 쓴다. 한 문장에 규칙 하나.
- 지금 필요한 만큼만 쓴다 (사전 대규모 설계 금지).

## 생명주기

지정(Specify) → 생성(Generate: AI가 뼈대와 테스트 스텁) → 검증(Validate) → 검토(Review: 사람) → 개선(Refine). 짧게 반복한다.

- AI로 요구사항 모으기: 원자료 요약 → 목표·품질·제약 추출 → FR/NFR/C 분류와 ID 부여 → **사람 검토(필수)**.
- 새 유스케이스는 **재생성**, 기존 동작 변경은 명세를 먼저 고친 뒤 영향받는 부분만 **동기화**한다.
- 코드 리뷰는 명세 확인 → 코드 대조 순서로 한다.
- 프로젝트 기억장치: `AGENTS.md`/`CLAUDE.md`(아키텍처 규칙), 스킬(반복 워크플로), MCP(최신 문서 접근).

## 테스트로서의 명세

- 메인 플로우 → 정상 경로 테스트, 대안 플로우 → 분기 테스트, 비즈니스 규칙 → 단언(assertion).
- 커버리지는 코드 줄 수가 아니라 **유스케이스의 모든 플로우와 규칙이 검증됐는지**로 잰다. 테스트 이름에 유스케이스 ID를 넣는다.
- 테스트 트로피: 정적 분석 → 단위 → 통합(핵심) → 브라우저 없는 UI 테스트 → 꼭 필요할 때만 Playwright E2E.
